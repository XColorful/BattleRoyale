> 项目: Custom BattleRoyale
> 移植目标: 26.1.2 → 26.2 NeoForge
> 基准版本: 26.1.2 (commit 607b68ae)

## 一、概述

最近一次 commit `alpha: Port to 26.2neoforge` 对 26 个文件进行了修改，其中约一半涉及渲染系统。由于对 26.2 最新的 GPU 驱动的渲染管线尚不熟悉，渲染部分的修改全部采用了临时占位 (placeholder) 方案，当前模组所有自定义渲染功能均处于**失效状态**。本报告将详细分析每一项渲染变更、追溯旧版本的渲染方式、解读 26.2 新渲染架构，并给出修复计划。

## 三、逐文件详细分析

### 3.1 CustomRenderType.java —— 自定义渲染管线定义

这是整个模组自定义渲染的**基石**。ZoneRenderer、TeamMemberRenderer、SpectatePlayerRenderer 都依赖此处定义的 RenderType。

#### 3.1.1 变更内容

**A. 基础 Snippet 从 `MATRICES_PROJECTION_SNIPPET` 变为 `DEBUG_FILLED_SNIPPET`**

```java
// 旧 (26.1.2)
RenderPipeline.builder(RenderPipelines.MATRICES_PROJECTION_SNIPPET)

// 新 (26.2, 占位)
RenderPipeline.builder(RenderPipelines.DEBUG_FILLED_SNIPPET)
```

**B. 顶点格式绑定方式从 `withVertexFormat` 变为 `withVertexBinding`**

```java
// 旧 (26.1.2)
.withVertexFormat(DefaultVertexFormat.POSITION_COLOR, VertexFormat.Mode.QUADS)

// 新 (26.2)
.withVertexBinding(0, DefaultVertexFormat.POSITION_COLOR)
```

**C. `bufferSize()` 方法被注释掉**

```java
// 旧 (26.1.2)
.bufferSize(RenderType.BIG_BUFFER_SIZE) // 4194304 bytes

// 新 (26.2)
// .bufferSize(RenderType.BIG_BUFFER_SIZE) // 方法已从 RenderSetupBuilder 移除
```

#### 3.1.2 旧版本（26.1.2）的实现方式

在 26.1.2 中，模组定义了两个自定义 RenderPipeline：

1. `SOLID_OPAQUE_COLOR_PIPELINE`: 基于 `MATRICES_PROJECTION_SNIPPET`，使用 `core/position_color` shader，不透明渲染
2. `SOLID_TRANSLUCENT_COLOR_PIPELINE`: 同上，但配置了半透明混合 (`BlendFunction.TRANSLUCENT`)

这两个 Pipeline 通过 `withVertexFormat(DefaultVertexFormat.POSITION_COLOR, VertexFormat.Mode.QUADS)` 同时指定了顶点格式（POSITION_COLOR）和图元拓扑（QUADS）。然后通过 `RenderSetup.builder(pipeline)` 创建对应的 `RenderType`，设置 `.bufferSize(RenderType.BIG_BUFFER_SIZE)` 来为大量顶点分配 4MB 缓冲区（模组渲染椭球等复杂形状时需要大缓冲）。

Pipeline 注册发生在 `RegisterRenderPipelinesEvent` 事件中，由 `_CustomRenderType` 监听并调用 `CustomRenderType.onRegisterRenderPipelines()`。

#### 3.1.3 26.2 的渲染系统更新

26.2 对整个渲染管线进行了根本性的重构：

- **`MATRICES_PROJECTION_SNIPPET` 不再存在**。旧的 snippet 体系被重新组织。26.2 的 snippet 更细粒度：`GLOBALS_SNIPPET`, `MATRICES_FOG_SNIPPET`, `BLOCK_SNIPPET`, `ENTITY_SNIPPET`, `TEXT_SNIPPET` 等。对于使用 `POSITION_COLOR` 格式的自定义渲染，最接近的是 `DEBUG_FILLED_SNIPPET`（定义在 `RenderPipelines` 第126行）。
- **VertexFormat 和 PrimitiveTopology 解耦**。旧 API `withVertexFormat(format, topology)` 合并了两个概念，新架构中 `withVertexBinding(bindingIndex, format)` 只声明顶点绑定，图元拓扑通过 `withPrimitiveTopology(topology)` 单独声明，或者由 snippet 继承。
- **`bufferSize()` 方法从 `RenderSetupBuilder` 中彻底移除**。26.2 使用新的 `StagedVertexBuffer` 内存管理体系，缓冲区大小不再由 RenderType 控制。

#### 3.1.4 当前占位方案的问题

当前使用 `DEBUG_FILLED_SNIPPET` 是**错误的**——它是 MC 调试用的 snippet，具有以下不适用的特性：
- 使用 `GREATER_THAN_OR_EQUAL` 深度测试（而非标准的 `LESS_THAN_OR_EQUAL`）
- 强制开启混合（`BlendFunction.TRANSLUCENT`）
- 没有 `FOG` bind group layout，可能导致与光影模组不兼容

### 3.2 ZoneRenderer.java, TeamMemberRenderer.java, SpectatePlayerRenderer.java —— 核心世界空间渲染器

这三个渲染器是模组最核心的视觉功能，负责在游戏世界中渲染区域形状、队友标记、观战玩家高亮。

#### 3.2.1 变更内容

三者模式几乎相同，以 ZoneRenderer 为例：

**A. `MultiBufferSource.BufferSource` → 直接创建 `BufferBuilder`**

```java
// 旧 (26.1.2)
MultiBufferSource.BufferSource bufferSource = mc.renderBuffers().bufferSource();
// ...
consumer = bufferSource.getBuffer(a < 0.999F ? TRANSLUCENT_ZONE : OPAQUE_ZONE);
// ... 绘制所有几何体 ...
bufferSource.endBatch();

// 新 (26.2, 占位)
// MultiBufferSource.BufferSource bufferSource = mc.renderBuffers().bufferSource();
// ...
consumer = new BufferBuilder(new ByteBufferBuilder(4096), PrimitiveTopology.QUADS, DefaultVertexFormat.POSITION_COLOR);
// ... 绘制所有几何体 ...
// bufferSource.endBatch(); // 注释掉了
```

**B. VertexConsumer → BufferBuilder 类型变更**

```java
// 旧 (26.1.2)
private @Nullable VertexConsumer consumer;

// 新 (26.2)
private @Nullable BufferBuilder consumer;
```

**C. 移除 MultiBufferSource import，添加 Blaze3D 底层 import**

```java
// 移除
import net.minecraft.client.renderer.MultiBufferSource;

// 添加
import com.mojang.blaze3d.PrimitiveTopology;
import com.mojang.blaze3d.vertex.BufferBuilder;
import com.mojang.blaze3d.vertex.ByteBufferBuilder;
import com.mojang.blaze3d.vertex.DefaultVertexFormat;
```

#### 3.2.2 旧版本（26.1.2）的实现方式

在 26.1.2 中，自定义世界空间渲染采用经典的 "立即模式 Buffer 拉取" 方式：

1. 通过 `Minecraft.renderBuffers().bufferSource()` 获取全局的 `MultiBufferSource.BufferSource`
2. 调用 `bufferSource.getBuffer(renderType)` 获取指定 RenderType 的 `VertexConsumer`
3. 向 `VertexConsumer` 写入顶点数据（位置、颜色、法线）
4. 调用 `bufferSource.endBatch()` 将缓冲区内容提交到 GPU 进行实际绘制

这种模式的优势是简单直接，缺点是隐式地依赖全局渲染状态。在 `IRenderLevelStageEvent` (AFTER_TRANSLUCENT_BLOCKS 阶段) 调用时，全局渲染状态已经被正确设置。

#### 3.2.3 26.2 的渲染系统更新

26.2 全面转向了**延迟提交节点 (Submit Node)** 系统：

- **`MultiBufferSource` 类被移除**。不再有全局的 buffer source 和 endBatch 机制。
- 所有渲染必须通过 `SubmitNodeCollector` 接口提交。`OrderedSubmitNodeCollector` 提供了 `submitCustomGeometry(PoseStack, RenderType, CustomGeometryRenderer)` 方法专门用于自定义几何体渲染。
- NeoForge 新增 **`SubmitCustomGeometryEvent`**：专门用于非实体/非方块实体的自定义几何体提交。事件提供：
  - `getSubmitNodeCollector()`: 提交节点收集器
  - `getPoseStack()`: 姿态矩阵栈
  - `getLevelRenderState()`: 包含相机、雾效等渲染状态
  - `getRenderableSections()`: 可见区块信息
- `mc.renderBuffers().bufferSource()` 不再存在。`mc.renderBuffers()` 返回的是旧的渲染缓冲区对象，它的 `bufferSource()` 方法已被移除。
- 新的获取方式：`mc.gameRenderer.renderBuffers()` 返回 `RenderBuffers`（用于面片缓冲池和 staged vertex buffer），但不提供 `bufferSource()`。
- `Camera` 可通过 `mc.gameRenderer.mainCamera()` 获取（而非 `mc.gameRenderer.getMainCamera()`）。

#### 3.2.4 当前占位方案的问题

当前方案直接创建 `BufferBuilder` 并写入顶点数据，但**完全没有提交到渲染管线**——`endBatch()` 被注释掉了。即使调用 `builder.build()` 获取 `MeshData`，也无人负责上传到 GPU 并发出绘制调用。几何体被"画到了空中"。

### 3.3 AbstractBlockRenderer.java 及相关文件 —— 方块实体渲染

涉及文件：`AbstractBlockRenderer.java`, `BlockModelRenderer.java`, `IBlockModelRenderer.java`, `EntitySpawnerRenderer.java`, `LootContainerRenderer.java`

#### 3.3.1 变更内容

**A. `MultiBufferSource` → `RenderBuffers` 全链替换**

所有方法签名中的 `MultiBufferSource` 替换为 `RenderBuffers`：
- `IBlockModelRenderer.renderBlockModel()` 签名
- `BlockModelRenderer.renderBlockModel()` 调用委托
- `AbstractBlockRenderer.renderBlockModel()` 调用处
- `AbstractBlockRenderer.render()` 抽象方法签名
- `EntitySpawnerRenderer.render()` 和 `LootContainerRenderer.render()` 实现

**B. buffer source 获取方式变更**

```java
// 旧 (26.1.2)
MultiBufferSource bufferIn = minecraft.renderBuffers().bufferSource();

// 新 (26.2)
RenderBuffers bufferIn = minecraft.gameRenderer.renderBuffers();
```

**C. Camera 获取方式变更**

```java
// 旧 (26.1.2)
Camera camera = mc.gameRenderer.getMainCamera();

// 新 (26.2)
Camera camera = mc.gameRenderer.mainCamera();
```

#### 3.3.2 旧版本（26.1.2）的实现方式

方块实体渲染器通过 `BlockEntityRenderer.submit()` 方法被调用。在该方法中：
1. 获取 `MultiBufferSource bufferIn = minecraft.renderBuffers().bufferSource()`
2. 调用 `renderBlockModel()` —— 最终通过 `NeoBlockModelRenderer` 实现，获取 `VertexConsumer` 并使用 `putBakedQuad()` 输出方块模型的每个面
3. 对于 LootContainerRenderer，在此基础上还进行物品渲染 (`ItemRenderer.renderStatic()`)

#### 3.3.3 26.2 的渲染系统更新

BlockEntityRenderer 的 submit 方法现在接收 `SubmitNodeCollector` 参数。理论上，方块模型渲染应该通过 `collector.submitBlockModel()` 或使用 `BlockStateModelPart` 来提交——这是新的"延迟提交"方式。

然而当前 `AbstractBlockRenderer.submit()` **忽略了传入的 collector 参数**，仍然尝试使用旧的"即时渲染 API"模式来渲染方块模型。

#### 3.3.4 当前占位方案的问题

`AbstractBlockRenderer.submit()` 获得了 `SubmitNodeCollector collector` 参数但完全未使用。整个渲染链传递 `RenderBuffers` 对象，但其方法 `bufferSource()` 已不存在。`NeoBlockModelRenderer.renderBlockModel()` 也被简化：移除了原有的 `VertexConsumer` + `putBakedQuad()` 逻辑，仅保留了 `BlockQuadOutput` 的回调设置（设置 lightCoords 和 overlayCoords），**但没有将几何体实际提交到渲染管线**。

### 3.4 Camera API 变更

```java
// 旧
Camera camera = mc.gameRenderer.getMainCamera();

// 新
Camera camera = mc.gameRenderer.mainCamera();
```

这是简单的 getter 重命名（从 `getMainCamera()` 到 `mainCamera()`），MC 标准化 getter 命名风格。

### 3.5 `bufferSize()` 方法移除

`RenderSetup.RenderSetupBuilder.bufferSize()` 在 26.2 中**完全移除**。26.2 使用新的 `StagedVertexBuffer` 系统管理缓冲区分配，RenderType 不再携带缓冲区大小信息。当前代码中被注释掉的 `.bufferSize(RenderType.BIG_BUFFER_SIZE)` 需要永远移除。

### 3.6 非渲染但相关的 API 变更摘要

- `BlockPos.getCenter()` → `Vec3.atCenterOf(BlockPos)`：Vec3 类的重构
- `ChatFormatting.getColor()` → `TextColor.fromLegacyFormat(f).getValue()`：颜色系统的重构
- `Team.setColor(ChatFormatting)` → `Team.setColor(Optional<TeamColor>)`：队伍颜色改为使用 `TeamColor` 枚举

## 四、26.2 渲染架构核心变化总结

### 4.1 即时模式 → 延迟提交模式

26.2 最大的架构变化是废弃了"即时模式"渲染（在事件回调中直接拉取 buffer、写顶点、endBatch），全面转向"延迟提交"系统：

| 特性 | 26.1.2 (即时模式) | 26.2 (延迟提交) |
|------|-------------------|-----------------|
| 缓冲区管理 | `MultiBufferSource.BufferSource` 全局管理 | `StagedVertexBuffer` |
| 提交方式 | `bufferSource.getBuffer()` + `endBatch()` | `SubmitNodeCollector.submit*()` |
| 顶点格式 | 在 `VertexConsumer` 写入时隐式确定 | 在 `RenderPipeline` / `RenderType` 中声明 |
| 渲染状态 | 全局 `RenderSystem` 状态机 | `RenderPipeline` 对象封装 |
| 自定义几何 | `RenderLevelStageEvent` 内直接绘制 | `SubmitCustomGeometryEvent` + `submitCustomGeometry()` |
| 方块模型 | `VertexConsumer.putBakedQuad()` | `submitModel()` / `submitBlockModel()` |

### 4.2 RenderPipeline 构建 API

```
旧: withVertexFormat(format, topology)  // 合并声明
新: withVertexBinding(index, format)    // 仅顶点绑定
   + withPrimitiveTopology(topology)    // 单独声明图元拓扑
```

### 4.3 Snippet 体系重组

26.2 重新组织了 `RenderPipelines` 中的 snippet：
- `GLOBALS_SNIPPET`：全局绑定组
- `MATRICES_FOG_SNIPPET`、`MATRICES_FOG_LIGHT_DIR_SNIPPET`：矩阵+雾+光照
- `BLOCK_SNIPPET`、`ENTITY_SNIPPET`：按方块/实体分类
- `DEBUG_FILLED_SNIPPET`：调试用填充几何（**不适合生产使用**）

### 4.4 关键类关系

```
SubmitCustomGeometryEvent
  ├── getSubmitNodeCollector() → SubmitNodeCollector
  │     └── submitCustomGeometry(poseStack, renderType, CustomGeometryRenderer)
  │           └── CustomGeometryRenderer.render(pose, vertexBuffer)
  ├── getPoseStack() → PoseStack
  └── getLevelRenderState() → LevelRenderState
        └── cameraRenderState → CameraRenderState (含相机位置等)
```

## 五、修改计划

### 5.1 优先级 1: 修复自定义 RenderPipeline（CustomRenderType.java）

**目标**：定义正确的、适用于生产的渲染管线，替代 `DEBUG_FILLED_SNIPPET`。

**计划**：
1. 将 snippet 从 `DEBUG_FILLED_SNIPPET` 改为 `GLOBALS_SNIPPET`
2. 手动添加 `BindGroupLayouts.MATRICES_PROJECTION`（替代旧的 `MATRICES_PROJECTION_SNIPPET` 功能）
3. 为半透明管线添加 `BindGroupLayouts.FOG`（使光影兼容）
4. 显式调用 `.withPrimitiveTopology(PrimitiveTopology.QUADS)`
5. 永久移除 `.bufferSize()` 调用（该方法已不存在）
6. 如有需要，微调深度测试/混合参数以匹配 `MATRICES_PROJECTION_SNIPPET` 的行为
7. 保持 Iris Shaders 兼容性（`IrisShaders.registerSolid/registerTranslucent` 调用不变）

### 5.2 优先级 2: 修复世界空间自定义渲染器（ZoneRenderer / TeamMemberRenderer / SpectatePlayerRenderer）

**目标**：将三个渲染器从"即时模式"迁移到 26.2 的"延迟提交"系统。

**计划**：
1. 创建新的 NeoForge 事件监听器，监听 `SubmitCustomGeometryEvent`
2. 在 `SubmitCustomGeometryEvent` 的处理器中：
   - 获取 `SubmitNodeCollector` 和 `PoseStack`
   - 从 `LevelRenderState.cameraRenderState` 获取相机位置
   - 对于每个需要渲染的区域/队友/观战玩家，调用 `collector.submitCustomGeometry(poseStack, renderType, renderer)`
   - 在 `CustomGeometryRenderer.render(pose, vertexBuffer)` 回调中执行实际的形状绘制
3. 需要为每个渲染器建立自己的 `ExtractLevelRenderStateEvent` 监听器（如果需要提取自定义渲染状态）
4. 移除旧的 `RenderLevelStageEvent` 注册（或改为向 `SubmitCustomGeometryEvent` 注册）
5. 将 `VertexConsumer consumer` 字段改为 `BufferBuilder consumer`（保持）

### 5.3 优先级 3: 修复方块实体渲染器（AbstractBlockRenderer 系列）

**目标**：纠正方块模型渲染流程，使其通过 SubmitNodeCollector 提交。

**计划**：
1. 在 `AbstractBlockRenderer.submit()` 中，使用传入的 `SubmitNodeCollector collector` 来提交方块模型
2. 研究 MC 26.2 原版如何使用 `submitBlockModel()` 方法渲染方块实体（参考原版 ChestRenderer、BeaconRenderer 等）
3. 可能使用 `collector.submitBlockModel(poseStack, renderType, parts, tintLayers, lightCoords, overlayCoords, outlineColor)` 方法
4. 需要将 `BlockStateModel` 拆解为 `List<BlockStateModelPart>`，或使用 Neoforge 扩展的 `submitMultiLayerBlockModel()` 方法
5. 对于物品渲染（LootContainerRenderer），研究 26.2 中 `ItemStackRenderState` 的新提交方式
6. 移除 `RenderBuffers` 参数传递链（不再需要手动传递 buffer 对象）

### 5.4 优先级 4: 清理和验证

1. 确认 `mc.gameRenderer.mainCamera()` 在所有使用点正确
2. 移除所有 `MultiBufferSource` 的残留 import
3. 清理注释掉的代码（`bufferSource.endBatch()`, `.bufferSize()`等）
4. 编译验证
5. 运行时验证：进入游戏、创建区域、验证区域形状可见性、队友标记、观战标记

### 5.5 修改风险点

- **光影兼容性**：新的 snippet 和 bind group 配置必须与 Iris Shaders 兼容。需要在有/无光影两种情况下测试。
- **Snippet 正确性**：`GLOBALS_SNIPPET` + `MATRICES_PROJECTION` bind group 是否等同于旧 `MATRICES_PROJECTION_SNIPPET` 的行为，需要对比旧版行为确认。
- **深度状态**：`DEBUG_FILLED_SNIPPET` 使用 `GREATER_THAN_OR_EQUAL` 深度测试，对不透明渲染是不正确的。新的 snippet 应使用标准 `DepthStencilState.DEFAULT`。
- **混合状态**：`DEBUG_FILLED_SNIPPET` 强制开启混合，不利于不透明渲染的性能。
